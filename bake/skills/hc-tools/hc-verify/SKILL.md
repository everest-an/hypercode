# hc-verify:交付前溯源比对自检

**目的**:任何 AI 生成的文档都存在"看起来对、实际错"的风险。本技能在交付前做最后一道闸:一切以用户提供的源材料为准。

## 工作流(四步)

### 1. 收集源材料
- 明确列出用户提供的全部输入:原始文档、数据表、对话中给出的数字/要求、附带的合同/论文/财报等。
- 若源材料不完整,先向用户索要,不要臆测。

### 2. 提取事实清单
从最终产出中逐类提取全部事实性陈述:
| 类别 | 例子 |
|---|---|
| 数字/金额 | "募资规模 5 亿"、"费率 2%" |
| 日期/时限 | "20 个工作日内备案"、"2026-08 上线" |
| 名称/机构 | 公司名、人名、条款名、法条号 |
| 引用/出处 | 引用的论文结论、判例、法规条文 |
| 技术行为 | 代码声称实现的功能、配置项的值 |

### 3. 逐条溯源(核心步骤)
对每一条事实:
- ✅ **可溯源**:在源材料中能找到对应位置 → 记录出处(文件/段落/行)。
- ❌ **不可溯源**:
  - 若该事实是推理得到的 → 标注【推断】并说明推理依据;
  - 若无依据 → **直接删除**该陈述,不保留。
- ⚠️ **与源材料矛盾** → 以源材料为准修正,并记入"变更说明"。

### 4. 一致性检查
- 同一事实在多处出现(正文/摘要/表格/PPT 页)必须完全一致,不一致的以源材料为准统一修正。
- 数字的合计、加总、百分比换算与源材料交叉验证。

## 交付格式(强制)

修正后的最终版必须附带:

```
## 溯源表
| # | 陈述 | 出处(源材料位置) | 状态 |
|---|---|---|---|
| 1 | ... | 源文件第 X 段 | ✅ 已核对 |
| 2 | ... | — | 【推断】依据:... |
| 3 | ... | (已删除,原陈述与源材料矛盾) | ✂️ 已修正 |

## 变更说明
- 修正了什么、为什么修正。
```

## 硬规则
1. **宁删勿错**:无法溯源的硬事实,删除优于保留。
2. **推断必须显式**:任何模型补全的内容必须可见地标注【推断】,不得混入事实。
3. **源材料优先**:产出与源材料冲突时,永远以源材料为准,不"圆场"。
4. **不做表面检查**:必须逐条列出事实再逐条溯源,禁止"大致看了一遍没问题"的结论。
