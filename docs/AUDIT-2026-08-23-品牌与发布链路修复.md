## 2. 修了什么(按用户能感知的程度排)

### 2.1 会损坏用户机器的

| 问题 | 根因 | 修法 |
|---|---|---|
| `setx PATH` 截断,永久破坏用户 PATH | cmd 里的 `%PATH%` 是 Machine+User 合并值,`setx` 无 `/M` 写入 User 作用域,且在 1024 字符处硬截断。实测开发机 PATH 有 **2092 字符** | 改用 `[Environment]::GetEnvironmentVariable("Path","User")` 只读用户作用域 + 精确分段判重 + 写回,**永不回写 `%PATH%`** |
| `hypercode upgrade` 把上游 OpenCode 装到用户机器 | `installation/index.ts` 零 diff,`upgradeCurl` 把 `opencode.ai/install` 管道给 sh。且**每次 TUI 启动**都检查,弹窗永远重复 | 删除 `upgradeCurl`;自动更新改 opt-in(`HYPERCODE_ENABLE_AUTOUPDATE`);releases 源指向 `AwareLiquid/HyperCode` |
| `hypercode uninstall` 卸掉用户真正的 OpenCode | 按 `# opencode` / `.opencode/bin` 标记清 shell rc —— 那些标记只有**上游**安装器会写;还执行 `npm/brew/choco/scoop uninstall` 上游包名 | 只清理 HyperCode 自己的标记与目录;移除所有非本产品的包管理器命令 |
| 桌面版 WSL 后端安装上游产品 | `wsl/runtime.ts:271` curl 上游 install 脚本,装完探测 `~/.opencode/bin/opencode` 当作自己的后端 | 无 Linux CLI 构建时明确失败;探测路径改 `~/.hypercode/bin/hypercode` |

### 2.2 让产品完全不可用的

**Windows 一键安装链路曾经是这样断的**(每一步都报告成功):

```
setx 截断毁 PATH
  → key「验证通过」是假的      curl 缺 -f,401 时仍 exit 0,空 key 也通过
  → 配置写进 %APPDATA%\hypercode  而引擎读 ~/.config/hypercode
  → 229 个技能同样写进错目录     一个都不加载
  → 屏幕显示「✔ 安装完成!key 验证通过。」
启动后
  → 引擎播种 apiKey: ""
  → 界面粘贴 key 被空串永久遮蔽 → 401,且唯一的自救手段失效
```

最后一环最隐蔽:`provider.ts` 的注入条件是 `options["apiKey"] === undefined`,而 `"" !== undefined`,所以配置里的空串会**永久遮蔽** auth store 里用户粘贴的真 key。修复做了双保险——播种不再写该字段,且注入条件改为 `!options["apiKey"]`,**已被旧版写坏配置的存量用户也能自动恢复**。

配置目录的错位值得单独记:`xdg-basedir` **没有任何平台分支**,所以 Windows 和 macOS 上引擎读的都是 `~/.config/hypercode`,不是 `%APPDATA%`、也不是 `~/Library/Preferences`。四个安装脚本现在统一走同一条回退链。

### 2.3 品牌泄漏

- **7 个 LLM 系统提示词**开头是 "You are opencode",并让用户去 `anomalyco/opencode` 提 issue。这是最用户可见的字符串
- **模型列表里有 7 个 `opencode/*`**。catalog 里其实有**两个**上游网关:`opencode`(OpenCode Zen,93 模型)和 `opencode-go`(OpenCode Go,28 模型)。后者在 `hypercode models` 里不显示(未认证的 provider 不列出),但会出现在 **ModelNotFound 的 suggestions** 里 —— 所以按命名空间 `/^opencode(-|$)/` 整体过滤
- 播种的用户配置写 `$schema: opencode.ai`,且**每次加载都改写用户文件**塞这个 URL
- 内置 skill 叫 `customize-opencode`,453 行正文教模型编辑配置,里面**全是错路径**
- 桌面通知从 opencode.ai 拉图标(品牌 + 外部请求 + 大陆可达性)
- Help 菜单、限额提示("订阅 OpenCode Go $5/月")、MCP 授权页的 `client_name`、发给每个 provider 的 User-Agent
- favicon 全套、PWA manifest 的 `name`(装到桌面时显示的应用名)

## 3. 新增能力:桌面版内置技能与插件

**背景**:229 个技能和 omo 插件都由 bake 脚本安装,而那是 CLI 流程,桌面版用户从不运行 —— 所以产品主打的能力对他们**根本不存在**。

### 3.1 技能(44 MB)

打进 `extraResources`,首次启动装到 `<config>/skills/hypercode-<group>/`,与 `bake.sh` 的命名空间约定一致。`hypercode-` 前缀标记系统区,**前缀外的用户自建技能永不触碰**。按 app 版本做标记,避免每次启动都复制;每个命名空间先写到 `.incoming` 再原子 rename,中断不会留下半份让引擎去加载。

### 3.2 插件(约 197 MB)

**为什么必须内置**:引擎装它要 230 个包 / 452 MB / 实测 2 分 37 秒,而 `arborist` 以 `progress: false` 运行,零反馈。桌面窗口是 `show: false` + `ready-to-show`,所以那段等待表现为**窗口根本不出现**,比空白窗口更像程序没启动。

**原理**:`Npm.add` 在 `<cache>/packages/<spec>/node_modules/<name>` 存在时短路返回,所以预填那个路径就把插件解析变成一次 `stat()`。

> ⚠️ **需要两个缓存目录,不是一个。** `Npm.add` 按 **spec 字符串**做 key,而两个插件加载器传的 spec 不同:
> - v1 `plugin/shared.ts` 把裸名重写成 `<name>@latest`
> - v2 `config/plugin/external.ts` 传裸名
>
> 只 seed 一个,另一个照样下载整棵树。第二个目录用硬链接克隆,不占额外空间。
> 配置里的 key 是 **`plugin`**(v1 会被迁移到 v2 形状),不是 `plugins`。

**体积**:450 MB 里 256 MB 是 `@code-yeongyu/comment-checker/vendor/` 下**五个平台**的二进制(每个约 52 MB),装一个包只需要一个。裁掉非目标平台 + 依赖的 docs/tests/sourcemap → 约 197 MB。

> **LICENSE 文件必须保留。** 压体积时很容易顺手删掉,那会让刚补齐的 Apache-2.0 / MIT 合规倒退。

## 4. 发布流程(新)

```
1. 编辑 /VERSION            ← 版本号唯一来源,发布号在 diff 里可审
2. 加 secret RELEASE_TOKEN  ← 对 AwareLiquid/HyperCode 有 contents:write
                              GITHUB_TOKEN 只能操作当前仓库,跨仓库发布拿不到权限
3. 手动触发 build-desktop,填 version
     → win-x64.exe / mac-arm64.dmg / mac-x64.dmg
     → 断言三个资产都在且都不小于 50 MB
     → 自动开 draft release
4. 人工验证安装包 → 点发布      ← draft 是刻意的:内部验证后再发布
5. 部署官网                     ← 下载链接指向 latest,发布后才通
```

**官网**(`AwareLiquid/AwareLiquid-Web` 的 `web/hypercode.html`):下载链接已改为 `/releases/latest/download/` 永久链接,**以后发版不用再改页面**。只提供桌面版(win + mac arm64 + mac x64),终端版已移除 —— 目标用户没有开发经验,不该拿到需要跑命令的 zip。

⚠️ 官网**没有自动部署**,push 到 GitHub 不等于上线,要另外在服务器(Caddy)部署。

## 6. 方法论:哪些检查会骗你

这次审计里,**三类问题绕过了全部现有检查**。记下来,因为它们会再来:

### 6.1 结构合法但内容为空

prod 图标的 ICO 头部、偏移、IHDR 全部有效,`file` 命令报告 "6 icons",大小检查也过 —— 但 16/32/48/64/128 帧的不透明像素是 **0.0%**。

> **只有解码像素才能发现。** 后来改用 favicon 时又踩了变种:那批图是 full-bleed,不透明比例**恒为 100%**,一个纯黑方块也能通过 —— 于是改用 **ink coverage**(明显亮于品牌背景的像素占比),并做变异测试(注入空白图必须失败)。
>
> 反例记录:我自己交叉验证时用"帧字节数"判断,把 152 字节的 16×16 帧标成"可疑过小",**那是误报**,解码后有 40/256 像素有墨迹。字节数和文件头都会骗人。

### 6.2 测试锁定了错误的行为

deep link 有测试,19 处断言,27 个全绿 —— 锁的全是改名前的 `opencode://` scheme,而产品注册的是 `hypercode://`。**测试通过恰恰是功能全死的伪装。**

同类还有:`electron-builder.config.test.ts` 是撞车事故的回归守卫,断言着改名前的 appId,而且因为没有 test script **从未运行过**。

### 6.3 两端各自正确但不相接

- 安装器写 `%APPDATA%`,引擎读 `~/.config` —— 每个文件单独看都合理
- `mcp add` 写 `hypercode.json`,而读取端只找 `opencode.json{,c}`
- `copy-metainfo.ts` 写 `ai.opencode.desktop.metainfo.xml`,打包配置读 `ai.awareliquid.hypercode.metainfo.xml`
- `setup.bat` 在 `bake/` 里却引用 `%HC_DIR%bake\...`,解析成 `bake/bake/`
- npm 发布管线:`bin` 用 `pkg.name`(仍是 opencode),校验和找 `opencode-*.tar.gz`,而 build 产出 `hypercode-*`

> **只有把读端和写端放在一起求值才会暴露。** 建议加 L1 守卫:断言 `bake/` 里的配置目录字面量与 `Global.Path.config` 的求值结果一致。

### 6.4 CN-trigger 补丁与 YAML

中文触发词被追加在了 block scalar 指示符**同一行**:

```yaml
description: > 中文触发词: 劳动合同;用工;...
  Cold-start setup — learns your...
```

YAML 规范要求 `>` / `|` 之后必须换行。严格解析直接失败 → 引擎的 gray-matter fallback 把整段当字面文本 → **description 开头留下 `"> "`**,而 description 正是注入给模型做技能选择判断的内容。229 个里只有 60 个能严格解析,169 个靠 fallback 苟活。

另一种形态:单行标量里的 `中文触发: ` 因为冒号+空格被当成嵌套映射。

**两种都统一规范化为 `>-` block scalar**(其内部 `: ` 不触发语法),内容一字未改。修完 229/229 严格解析通过。
